# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Project

A full redesign, from scratch, of **aod.co.in** for AOD (Artists on Demand), an Ahmedabad marketplace for booking photographers, cinematographers, DJs, anchors, makeup artists and other event talent. The goal of the rebuild is a site that feels **more trustworthy** and has real booking and artist data, unlike the old site, which had no backend and only opened WhatsApp.

- `context/brief.md` holds the owner's raw notes for the redesign: features, nav, homepage sections and references. Read it before planning any page.
- `context/*.html` is a saved copy of the Upwork homepage, the main visual reference (layout, colours, typography). Other references: Urban Company, Snabbit, collectui.com.

## Commands

```bash
npm run dev     # dev server at http://localhost:3000
npm run build   # production build (also type-checks)
npm run lint    # ESLint (next/core-web-vitals + typescript)
npm run check:search   # checks search results for common queries and misspellings
npm run check:links    # checks the artist portal's portfolio-link rules
npm run check:pay      # checks the payment page's UPI rules (amounts, UTR, upi:// links)
npm run check:db       # runs the database migrations on PGlite and checks who can read and change what
```

There is no test runner yet. The `scripts/*-check.mts` files are plain Node scripts (run through Node's built-in TypeScript support). Add a case there when you change search keywords or tuning, the link rules, the UPI helpers or the database's access rules.

Copy `.env.example` to `.env.local` and fill it in. Without the Supabase URL and publishable key the site runs as the preview (see Backend below); `docs/backend-setup.md` is the step-by-step guide to switching the backend on (Supabase project, SQL, first owner, sign-in code emails, keys, Resend, the Google Sheet, retries).

## Stack

- **Next.js 16 (App Router, `src/` dir) + React 19 + TypeScript.** This version has breaking changes from older Next.js. Check `node_modules/next/dist/docs/` before using an API you're unsure of (e.g. `middleware` is now `proxy`).
- **Tailwind CSS v4.** There is no `tailwind.config`. Design tokens live in the `@theme` block in `src/app/globals.css`.
- **Supabase** for the database and sign-in (emailed 6-digit codes for customers, artists and staff). Use `src/lib/supabase/server.ts` in Server Components/Actions (it acts as the signed-in user, so row-level security applies), `src/lib/supabase/client.ts` in Client Components, and `src/lib/supabase/admin.ts` (secret key, skips row-level security) only in server code after checking the input or the caller. Create a new server client per request.
- **WhatsApp** stays the main contact channel. Build all `wa.me` links through `whatsappUrl()` in `src/lib/whatsapp.ts`.
- Hosted on Vercel. Visitors are in India, so prefer static or cached rendering, and run server functions in the Mumbai region (`bom1`).

## Backend

- **Two modes**, picked by `backendEnabled` (`src/lib/backend.ts`: the Supabase URL and publishable key are set). Live: every form saves to the database first, sign-in sends real codes, and the admin works on shared data. Preview (no keys): the site behaves as the frontend-only version (WhatsApp hand-off, samples, admin data in the browser). Every live feature keeps its preview fallback, so the deployed site never breaks while keys are missing.
- **Database**: `supabase/migrations/20261009000000_init.sql` (run once in the SQL Editor). Tables mirror the admin records in `src/lib/admin-store.ts` (applications, artists, bookings, payments, payouts, leads, cases, staff, activity, settings) plus `outbox` for retries. IDs are the readable references (B-1215, APP-201, PAY-3101, L-401, RC-1001, U-1; a website request is AOD-<first booking number>, one booking per category it needs). Row-level security: active staff (listed in `staff`, matched by the signed-in email) read everything; writes follow the admin roles (owner/ops: applications, artists, leads, resolution cases; owner/ops/finance: bookings, payments; owner/finance: payouts; owner: team, settings); a customer reads only bookings and payments made with their email (never cases: tracking a case goes through the server with its number and email); signed-out visitors get nothing. `src/server/rows.ts` maps rows to the admin types. `npm run check:db` (`scripts/db-check.mts`) runs the migrations on PGlite (Postgres in Node, with Supabase's auth stand-ins) and checks each kind of user's access; add a case there when changing the rules.
- **Server actions** (`src/server/actions/`): `auth.ts` (request and verify an emailed code; staff only if their email is in `staff`), `public.ts` (booking request, artist application, payment report: validated, honeypot field `website`, saved with the secret key), `resolution.ts` (raise, track and escalate a Resolution Centre case; tracking needs the case number plus the email it was raised with and never returns internal notes or staff names), `customer.ts` (My bookings, reviews), `admin.ts` (`adminSession`, `loadAdminDb`, `saveAdminChanges`). In live mode `admin-store.ts` loads the whole `Db` once and each `update()` sends only the records it added, changed or removed; the server checks the role and row-level security checks it again; a refused save reloads the data and shows why. New records insert (never upsert), so two people taking the same number get an error instead of overwriting each other.
- **After a save** (`after()` in the actions, `src/server/notify.ts`): a row on the Google Sheet's "All orders" tab and on the tab named after each category (service account, `ORDERS_SHEET_ID`), and emails through Resend (team notifications follow admin Settings → notify; customers and artists get a confirmation). A job that fails or lacks keys waits in `outbox`; `GET /api/jobs/retry` with `Authorization: Bearer <CRON_SECRET>` retries it (up to 6 times).
- **Not live yet**: the artist portal's signed-in pages (still browser samples), uploading portfolio files to storage (live applications require a portfolio link), authenticator-app 2FA for staff (email codes for now), DigiLocker KYC and Razorpay.

## Code layout

- **`src/content/site.ts` holds all site copy and data** (categories, services, sample artists, stats, page text), carried over from the old aod.co.in. Pages and components read from it, so copy changes happen there, not in JSX. Ratings, counts and the escrow claim in it are sample data, flagged at the top of the file.
- `src/app/`: routes. The root `layout.tsx` only sets up `<html>`, the font, metadata and `MotionProvider`. The customer site lives in the `(site)` route group (the group doesn't change URLs), whose `layout.tsx` adds `Navbar`, `Footer`, `WhatsAppFab` and `ScrollProgress`. In it, `page.tsx` is the homepage, which only composes sections, and `categories/[slug]` is statically built from `categories` through `generateStaticParams`. There are also `book/`, `business/`, `for-artists/` and `about/` (About us: intro with facts drawn from `site.ts`, story, values, the brand strip, the founders with photo placeholders, and a contact grid; copy in `about` in `site.ts`, where the founders' names and titles are flagged to confirm). `not-found.tsx`, `sitemap.ts` and `robots.ts` stay at the root; `not-found.tsx` renders the navbar and footer itself because only the root layout wraps it. The artist portal is `artists/` (see below).
- `src/components/home/`: one file per homepage section. The order follows the visitor's decision path, modelled on booking marketplaces (Urban Company, Upwork): hero (full screen) → announcement bar → stats ("Relied on across Gujarat": four number cards in one font, each with a small graphic picked by `visual` in `stats` (avatars with a check, `Stars` from `ui/Rating.tsx`, category icons, a handshake), with the shared card animation, ending in the "Trusted by renowned brands" logo strip) → category grid → most booked (list) → verified-artists trust section → portals (`Portals`, "Everything in one place": a dark artist band, "Are you an artist? Join AOD.", with perks and two large links, Join as an artist (`/artists/apply`) and Sign in to the artist portal (`/artists`), then four cards with the shared card animation for My bookings, Pay AOD, the Resolution Centre and AOD for Business, each showing its address; copy in `portals` in `site.ts`) → how it works (numbered steps, no photos) → features (cancellation, reschedule…) → get-matched (intro, a "What happens next" timeline and "Prefer to talk?" on the left, sticky and shown on laptops only; the quiz on the right; copy in `getMatched` in `site.ts`) → booking options (personal / business) → final call to action. `src/app/(site)/page.tsx` comments the reason for each position.
- Brand strip (`src/components/home/BrandStrip.tsx`): logos of brands that trust AOD, listed in `clientBrands` in `site.ts`, scroll right to left without end (CSS `animate-marquee` in `globals.css`, never pauses, a still wrapped row under reduced motion). Logo files are in `public/brands/`, cut out of their backgrounds as transparent PNGs, cropped tight and 160–240px tall. The originals the owner sent are in `context/brands/`. Each logo gets the same visual area rather than the same height, so wide and square logos look balanced. Some logos were adjusted to suit a white strip: HoneyVeda's flower sits to the left of the wordmark, KYB Conmat's white lettering is charcoal, and Ganesh Housing's small print is removed. The GATE 2026 expo logo comes from the expo's own artwork (navy lettering, transparent) and sits half a loop away from the round GCCI badge. The loop runs 63 s for 26 logos at their current size (`AREA` / `MAX_HEIGHT` in `BrandStrip.tsx`); lengthen it in proportion when adding or enlarging logos so the speed stays the same.
- `src/components/layout/`: navbar (client component, for the mobile menu and the category dropdown; no WhatsApp link, contact is the floating button; "How it works" and "About us" drop out of the desktop bar between 1024 and 1280px), announcement bar, footer (contact: phone, email and the Instagram handle; Follow us: Instagram, LinkedIn, WhatsApp; the LinkedIn icon hides if `brand.linkedinUrl` is empty) and `WhatsAppFab` (bottom-right rounded square with the WhatsApp logo in WhatsApp's own green, `bg-whatsapp` = #25d366, that widens to "Chat on WhatsApp" on hover or keyboard focus).
- `src/components/ui/`: shared building blocks. `Container` sets the page width: small side gutters, capped at `max-w-page` (about 1600px, `--container-page` in `globals.css`) and centred, so very wide or zoomed-out screens don't stretch the layout; section backgrounds sit outside it and still run full width. The navbar's contents use the same cap; the footer is a full-width dark band whose contents use it. `Button` provides `buttonClasses()` and `ButtonLink`, which opens external, `tel:` and `mailto:` links as plain anchors. `Icon` maps icon names from `site.ts` to lucide icons and also draws the WhatsApp, Instagram and LinkedIn SVGs. `PhotoPlaceholder` stands in for real photos. `StepFlow` shows numbered steps without photos (icon badges joined by a line on laptops, a timeline on phones); it's used by How it works and the For Artists "How joining works" steps. `Rating` shows star ratings.
- Search: `src/lib/fuzzy.ts` holds the ranking and typo tolerance. It has no imports, so it can be tested on its own. Matching works on whole words, sound-alike spellings (ph→f etc.) and edit distance, and categories outrank single services. Search words for each category live in `keywords` in `site.ts`. `src/lib/search.ts` builds the index from `site.ts`. `src/components/search/SearchBox.tsx` is the navbar input with suggestions, arrow-key navigation and a no-match fallback to `/book`. The navbar shows it inline from 1024px up (the "How it works" and "About us" links hide between 1024 and 1280px to make room); below 1024px it is an always-visible full-width bar under the logo row. While empty and unfocused, the placeholder types random categories and services (word swaps only under reduced motion).
- Interactive parts are small client components (`Navbar`, `SearchBox`, `CityPicker`, `MatchQuiz`, `HowItWorks`, `Coverflow` (via `CategoryCoverflow`), `HeroMotion`, `HeroVideo`, `VerifiedSection`, and the artist portal's forms and pages). Everything else is a Server Component, and every route is prerendered as static.
- Animation uses **Motion** (`motion/react`, v14). Shared pieces are in `src/components/motion/`: `Reveal` / `StaggerList` (scroll-in), `TiltCard` (see Cards below), `ScrollProgress`, and `MotionProvider` (sets `reducedMotion="user"` site-wide). Homepage set pieces: one carousel only, the 3D coverflow slide (`src/components/motion/Coverflow.tsx`) for the categories, each card showing the category photo (`image` in `site.ts`, files in `public/categories/`) with the category icon on a small tile; side cards sit further back in 3D so they never cut into the front card. "Most booked services" (`MostBooked`) is a list (a terracotta diamond bullet, service, category, rating, link; two columns on laptops) with no photos and no cards. The carousel supports mouse / touch drag, unlimited trackpad two-finger swipe, dots, arrow buttons and ← → keys, the pointer glow and booking walk-through (`HeroMotion`: `HeroDemo` spotlights one step at a time, popping it forward while the other two grey out, cycling every 1.2 s while on screen; all lit and still under reduced motion), and the scroll-driven dark section (`VerifiedSection`). The search placeholder types random categories and services (`useTypedPlaceholder` in `SearchBox`).
- Cards: every repeating card on the customer site uses the same animation as "Book with confidence": the grid is a `StaggerList` of `StaggerItem`s (cards arrive in a wave), each card is a `TiltCard` (3D tilt towards the pointer, slight grow, a light that follows the cursor; `tone="dark"` on dark backgrounds, `fill={false}` when text sits under the card), with `cardHover` (border warms) on the card and `iconHover` (icon pops and turns) on its icon, both exported from `TiltCard.tsx`. Use the same pieces for any new card grid. Carousel cards, app lists (My bookings, artist portal, admin) and large panels don't tilt.
- Animated elements render their final content on the server and carry `data-reveal`; a `<noscript>` rule in `layout.tsx` makes them visible when JavaScript is off. Keep both when adding animations.
- Trust message: every artist is described as **thoroughly verified** (`verifiedArtists` in `site.ts`, shown by `VerifiedArtists` in three sizes and the homepage `VerifiedSection`). The site doesn't promise meeting artists in person, either as a vetting claim or as a customer feature: the "Book with confidence" card and the personal booking option say "Every artist verified thoroughly" instead. (The admin's applicant "Meeting scheduled" stage is the team's internal vetting step.) The hero is the brand name as the page `<h1>`, the subtitle, the verified pill, the two buttons and "Join AOD", full screen and edge to edge over the background video (a light veil keeps the footage about 90% visible; soft text shadows keep the white text readable, the brand name as static embossed chrome lettering: two layers of the same text, `text-emboss-edge` (raised bevel and shadow) under `text-emboss-face` (brushed steel), in `globals.css`; no scramble or other text animation), with the booking walk-through on the right in a narrower panel of dark, lightly blurred glass, set a little below centre. The hero is `100svh` minus the sticky navbar, and the announcement bar sits just below it. The footage (GATE 2026 expo coverage, trimmed of its fade-in so the loop stays bright) is in `public/media/`, or at `NEXT_PUBLIC_MEDIA_URL` when that points to a storage bucket or CDN with the same file names: AV1 and H.264 cuts at 1920×1080 (`hero-1080*`) and 680×1210 for phones held upright (`hero-portrait*`, picked by `(max-aspect-ratio: 2/3)`), 30 fps, no sound, plus WebP posters of the first frame (`hero.webp`, `hero-portrait.webp`). `HeroVideo` renders the poster on the server and only adds the video once the page has loaded, fading it in when it plays; there's no video under reduced motion, Data Saver or 2G. Keep the AV1 files around 3 MB (laptop) and 1.5 MB (phone) when replacing the footage. Matches are "curated matches" (no fixed number).
- Booking flow: every "book" button goes to `/book`, the choosing screen (For personal events / For business). Each choice leads to `/book/personal` or `/book/business`, which run `MatchQuiz` with that audience's occasion list (`occasions` in `site.ts`). `MatchQuiz` asks the three questions one at a time, sliding between them: picking the occasion moves straight on, the answers so far show as chips that jump back to edit, and focus moves to each new question once it has slid in.
- **My bookings** (`/my-bookings`, `src/components/bookings/MyBookings.tsx`): the customer's view of their orders, reached from the outlined "My bookings" button in the navbar (icon-only between 1024 and 1280px and on phones) and the phone menu. Sign-in is an emailed 6-digit code. Live: it lists the bookings made with that email (`myOrders`), shown by request reference and booking id, and saves reviews (`submitReview`). Preview: any code works, and it lists the requests this browser sent from the booking form (`src/lib/customer-store.ts`) plus sample bookings labelled "Sample" (`src/content/my-bookings.ts`). Each booking has progress steps, the next action (pay advance/balance through `/pay`, download files), event, artist, payments, help and timeline. Browser-kept stores share `createStore` from `src/lib/local-store.ts`.
- City: the navbar `CityPicker` (and `CityChips` in the mobile menu) saves the visitor's city through `src/lib/city.ts`, which keeps it in localStorage (`aod-city`) and reads it with `useSyncExternalStore`. `MatchQuiz` reads the same value, shows "City selected: …" with a Change option instead of asking again, and puts it in the WhatsApp message. In live mode the city is saved with the booking request.
- Artists join by a pre-filled WhatsApp message (`artistJoinMessage` in `site.ts`), or through the artist portal's application form, which ends with the same WhatsApp hand-off until the backend exists.
- **Artist portal** (`src/app/artists/`, planned for `artists.aod.co.in`): a frontend preview with no backend. `artists/page.tsx` is sign-in (one-time code by WhatsApp or email; any 6 digits work in the preview), `artists/apply` is the five-step application (`ApplyForm`), and the `(portal)` route group holds the signed-in pages: `dashboard`, `profile`, `portfolio`, `bookings`, `availability` and `documents`, with a sidebar (`PortalNav`, tabs on phones) and the account menu. Copy and sample data (sample artist, booking requests, onboarding stages, upload limits) are in `src/content/artist-portal.ts`; components are in `src/components/artists/`. Answers, profile edits, booking actions, blocked dates and the "Preview as live artist / new applicant" switch are kept in this browser through `src/lib/artist-store.ts` (localStorage + `useSyncExternalStore`, like `city.ts`); uploaded files stay in the tab only (object URLs). There is no site-wide preview banner; instead the places where it matters say so (the sign-in code, file uploads, DigiLocker, quotes), and the submit screen says the application was not sent and offers WhatsApp instead. Portfolio links are checked by `src/lib/portfolio-links.ts` (no imports; tested by `check:links`).
- The portal is linked from the homepage's portals section, the For Artists page ("Apply online" and "Sign in" links) and the footer's For artists column; it carries `noindex` and `robots.ts` disallows `/artists`, `/pay` and `/admin`. `src/proxy.ts` serves each separate site at the root of its own domain: hosts starting with `artists.`, `pay.`, `admin.` or `resolve.` (so `http://admin.localhost:3000` works locally), plus hosts listed in `ARTISTS_HOSTS`, `PAY_HOSTS`, `ADMIN_HOSTS` and `RESOLVE_HOSTS` (e.g. `*.vercel.app` domains added to the same Vercel project). Links inside the portal use `/artists/...` paths, which work on both hosts. On the artists host `/` is the portal, so links back to the customer site use `mainSiteUrl` (from the `NEXT_PUBLIC_SITE_URL` env var).
- **Payment page** (`src/app/pay/`, planned for `pay.aod.co.in`): takes payment by UPI with no gateway. `PayFlow` runs three steps: details (amount, purpose, name), pay (a QR code drawn in the browser by `UpiQr` from a `upi://` link, app buttons for Google Pay / PhonePe / Paytm with Android and iPhone schemes, the UPI ID to copy, optional bank-transfer details), then the 12-digit UPI transaction ID, sent to AOD on WhatsApp. It ends on "Waiting for AOD to confirm" and never says paid. A link made in the admin (`?amount=&ref=&for=&name=`) fills in and locks the amount. The payee comes from `NEXT_PUBLIC_UPI_ID` / `NEXT_PUBLIC_UPI_NAME` (and optional `NEXT_PUBLIC_BANK_*`); without a UPI ID the page asks the customer to message AOD instead of showing a QR. UPI helpers are in `src/lib/upi.ts` (no imports; tested by `check:pay`); copy in `src/content/payments.ts`. Razorpay (cards, netbanking, automatic confirmation) slots in where the "coming soon" row is.
- **Resolution Centre** (`src/app/resolve/`, planned for `resolve.aod.co.in`): a formal place, separate from WhatsApp support, for customers, businesses and artists to raise a problem with a booking. Its own small header and footer (like the payment page), indexable, canonical `aod.co.in/resolve`. `/resolve` explains it (promises: a reply within 48 hours, a decision within 30 days, escalation to the grievance officer; how a case works; who can raise one and about what; the grievance officer and the National Consumer Helpline), `/resolve/new` is the form (`CaseForm`: who you are, what went wrong, booking number, date, description, the outcome wanted, optional evidence links, contact details and a confirmation; `?role=` and `?ref=` pre-fill it, and My bookings links each booking to it), and `/resolve/track` (`TrackCase`) shows a case's progress and AOD's decision from its number and email, with an Escalate button. Live, cases save to `cases` (RC-1001…) and email the team and the person; in the preview the form hands the case to WhatsApp and says it was not saved, and tracking offers a sample labelled "Sample". Copy in `src/content/resolution.ts` (drafts for the founder to confirm: the time promises and the grievance officer's name); staff handle cases in the admin's Resolution cases page. Deploying `resolve.aod.co.in` is a domain in Vercel plus a DNS record (`docs/backend-setup.md`, section 8).
- **Admin panel** (`src/app/admin/`, planned for `admin.aod.co.in`): live on the database when the backend is set up (see Backend), otherwise a preview on sample data. `/admin` is staff sign-in: live, a work email listed in Team & roles and an emailed code (no role picker, no sample-data badge, no reset); preview, any details with a role picker and an "Open as Owner" shortcut. The `(panel)` route group has Overview, Applications (review → meeting → trial → approve, which creates the artist), Artists, Bookings (drag-and-drop board and table; matching with clash and day-off checks, quotes, payment links, recorded payments, delivery link, review, reschedule/cancel, history), Calendar, Payments (verify UTRs, which confirms the booking; payouts; payment-link builder), Leads (convert to booking), Resolution cases (status, the decision the person sees, internal notes, a 48-hour reply / 30-day decision countdown; new and escalated cases show in the nav count and Needs attention), Messages (WhatsApp templates filled from a record), Reports & exports (stats and a master Excel workbook with one sheet per list), Team & roles (owner / ops / finance / viewer; every role sees every page, roles gate the actions), Activity log and Settings. Data goes through `src/lib/admin-store.ts` (live: loaded from and saved to Supabase; preview: one localStorage object seeded from `src/content/admin-sample.ts`, where phones start with 55 and emails use example.com so nothing reaches a real person); every change goes through `update()`, which writes the activity log. Pipelines, roles, permissions and templates are in `src/content/admin.ts`; components in `src/components/admin/` (`AdminShell`, `DataTable`, `ui.tsx`, `pages/`). Records open in a drawer through `?open=<id>` (`useOpen`). Excel files are written by `src/lib/xlsx.ts` (a small dependency-free .xlsx/CSV writer).
- **Policies**: `/privacy`, `/terms` and `/refund-policy` (in the `(site)` group) render `src/content/legal.ts` through `src/components/legal/LegalPage.tsx`. They are linked from the footer's Policies & help column (which also links the Resolution Centre), the phone menu, the booking request's send step, the payment page, the artist application and the artist portal footer (`PortalFooter`), and listed in admin Settings. They are drafts marked "Draft": the legal entity name, GSTIN and grievance officer are "[to add]", the refund cut-offs and percentages are proposals for the founder to confirm, and a lawyer should check them before real payments. Links to them from the artists, pay and admin domains go through `siteHref()` (`src/lib/site-url.ts`).
- Identity checks in the portal go through DigiLocker via a KYC provider (`DigiLockerCard`); there is no Aadhaar number field or Aadhaar card upload, and payout details (bank/UPI, PAN) are only asked for after the trial booking.
- Booking requests, artist applications and payment reports save to the database first (live mode) and only then say "received" with their reference; WhatsApp still opens afterwards (through `whatsappUrl()`, with the reference in the message), and if saving fails the visitor is told and WhatsApp carries the request instead. Every field of an event request is required, on the website's booking quiz and the admin's New booking form alike: date (from tomorrow), start and end time, city, event details, name, phone and email. Times are stored as HH:MM start and end (`time` / `endTime`, columns `event_time` / `event_end_time`; an end earlier than the start means the event runs past midnight) and shown through `src/lib/event-time.ts` (no imports) as "8:00 PM – 1:00 AM (5 hours, ends next day)" in the forms, WhatsApp message, emails, the sheet's Time column, the admin and My bookings.

## Design system

Terracotta & cream with espresso text (warm, welcoming and professional), with the layout modelled on Upwork. The token names `peach`, `apricot` and `tangerine` date from the first orange theme; their values are now terracotta shades. Feature bands use the `bg-sheen` (light, ink text) and `bg-sheen-deep` (terracotta middle, white text) utilities, plus `grain` for a fine film-grain texture (the announcement bar and the closing call-to-action bands). The AOD wordmark (`public/aod-wordmark.png`) is in the brand terracotta. App icons (in `src/app/`, picked up by Next automatically): the browser-tab icon (`favicon.ico` at 16/32/48 and `icon.png` at 512) is an "A." monogram cut from the wordmark, white on a terracotta rounded square, because the full "AOD." blurs at 16px; the phone home-screen icon (`apple-icon.png`, 180) shows the full "AOD.". WhatsApp keeps its own green. Use the token classes (`text-ink`, `bg-brand`, `hover:bg-brand-hover`, `bg-peach`, `text-apricot`, `text-tangerine`, `bg-wash`, `border-line`, `text-muted` …), never raw hex values. The font is Inter, loaded with `next/font`, as a free stand-in for Upwork's paid Neue Montreal. Real artist photos are the main trust signal, so design cards and pages around photos, not icons. The category photos in `public/categories/` (`image` in `site.ts`) are mock photos for the preview (copied from another working copy of the project); replace them with real AOD artists' work before launch. They show in the category carousel and on each category page, where the photo sits on the right of the dark header, fully visible at the right edge and fading into the dark towards the left (a CSS mask). From tablets up the photo box keeps the photo's own shape (`image.width` / `image.height` in `site.ts`) at the header's full height, so nothing is cropped; on phones it fills the header faintly behind the text.

## Rules carried over from the old-site audit

- Never show "received" or "confirmed" for a booking or artist application unless it has actually been saved (to Supabase). Opening WhatsApp is not saving.
- No hardcoded ratings, review counts, artist counts or "bookings" numbers. Show only real data, or leave the element out.
- Don't claim escrow, payments or verification that aren't built yet.
- Don't collect Aadhaar numbers. Identity checks must go through a proper KYC provider such as DigiLocker.
- The site needs privacy, terms and cancellation/refund pages before it collects personal data or payments. Drafts exist (see Policies above); they must be confirmed and reviewed before launch.
- Every page needs a title, a description, Open Graph tags and a share image, because links are mostly shared on WhatsApp. Also provide `sitemap.ts` and `robots.ts`.
- Render key numbers and content on the server so they show up without JavaScript (the old site showed "0 verified artists" to crawlers).
