## Project

A full redesign, from scratch, of **aod.co.in** for AOD (Artists on Demand), an Ahmedabad marketplace for booking photographers, cinematographers, DJs, anchors, makeup artists and other event talent. The goal of the rebuild is a site that feels **more trustworthy** and has real booking and artist data, unlike the old site, which had no backend and only opened WhatsApp.

- `context/brief.md` holds the owner's raw notes for the redesign: features, nav, homepage sections and references. Read it before planning any page.
- `context/*.html` is a saved copy of the Upwork homepage, the main visual reference (layout, colours, typography). Other references: Urban Company, Snabbit, collectui.com.

## Commands

```bash
npm run dev     # dev server at http://localhost:3000
npm run build   # production build (also type-checks)
npm run lint    # ESLint (next/core-web-vitals + typescript)
npm run check:search   # checks search results for common queries and misspellings
npm run check:links    # checks the artist portal's portfolio-link rules
npm run check:db       # runs the database migrations on PGlite and checks who can read and change what
npm run check:orders   # checks that the booking form's WhatsApp message reads back into the admin's New booking form
```

There is no test runner yet. The `scripts/*-check.mts` files are plain Node scripts (run through Node's built-in TypeScript support). Add a case there when you change search keywords or tuning, the link rules, the database's access rules or the booking form's WhatsApp message.

`docs/DEVELOPER_GUIDE.md` is the guide for human developers (stack, folder by folder, flows, cookbook, errors); keep it in step with changes, like this file.

Copy `.env.example` to `.env.local` and fill it in. Without the Supabase URL and publishable key the site runs as the preview (see Backend below). The setup and testing guides live outside the repo, in `E:\Projects\Internship\aod docs\` (the folder next to this one), because they hold the project's passwords; never move them back into the repo. `backend-setup.md` there is the step-by-step guide to switching the backend on (Supabase project, SQL, first owner, sign-in code emails, keys, Resend, the Google Sheet, retries, subdomains), and `testing.md` is how to test everything: the automated checks, the preview, and a live walk-through across three browsers (staff, customer, artist). Keep it in step when adding a flow.

## Stack

- **Next.js 16 (App Router, `src/` dir) + React 19 + TypeScript.** This version has breaking changes from older Next.js. Check `node_modules/next/dist/docs/` before using an API you're unsure of (e.g. `middleware` is now `proxy`).
- **Tailwind CSS v4.** There is no `tailwind.config`. Design tokens live in the `@theme` block in `src/app/globals.css`.
- **Supabase** for the database and sign-in (emailed 6-digit codes for customers, artists and staff). Use `src/lib/supabase/server.ts` in Server Components/Actions (it acts as the signed-in user, so row-level security applies), `src/lib/supabase/client.ts` in Client Components, and `src/lib/supabase/admin.ts` (secret key, skips row-level security) only in server code after checking the input or the caller. Create a new server client per request.
- **WhatsApp** stays the main contact channel. Build all `wa.me` links through `whatsappUrl()` in `src/lib/whatsapp.ts`.
- Hosted on Vercel. Visitors are in India, so prefer static or cached rendering, and run server functions in the Mumbai region (`bom1`).

## Backend

- **Two modes**, picked by `backendEnabled` (`src/lib/backend.ts`: the Supabase URL and publishable key are set). Live: every form saves to the database first, sign-in sends real codes, and the admin works on shared data. Preview (no keys): the site behaves as the frontend-only version (WhatsApp hand-off, samples, admin data in the browser). Every live feature keeps its preview fallback, so the deployed site never breaks while keys are missing.
- **Database**: the files in `supabase/migrations/`, each run once in date order in the SQL Editor (`…_init.sql`, `…_live_and_artists.sql`, `…_no_pay_page.sql`, then `…_details_and_developers.sql`, `…_outbox_rule.sql`, `…_team_bookings.sql` and `…_one_order_per_request.sql`; add a new dated file for any change, never edit one that may have been run, and run a new one before deploying the code that uses it). Tables mirror the admin records in `src/lib/admin-store.ts` (applications, artists, bookings, payments, payouts, leads, cases, staff, activity, settings) plus `artist_replies` (an artist's quote or decline for a booking they're shortlisted for), `outbox` for retries, and the public `portfolio` storage bucket (artists' photos and videos, listed in `artists.portfolio` / `applications.portfolio`). IDs are the readable references (B-1215, APP-201, PAY-3101, L-401, RC-1001, U-1; a website request is one booking however many kinds of artist it needs, and the customer's reference AOD-<the same number>). Row-level security: active staff (listed in `staff`, matched by the signed-in email) read everything; writes need one of the two staff roles, owner (shown as "Admin") or developer (`staff_can()` lets a developer through every owner rule; the policies still list the old ops / finance roles, which the role check no longer allows); customers and artists read nothing directly: My bookings, the artist portal and case tracking go through server actions that check who is signed in and return only what that person should see (no internal notes, shortlists or other people's details); signed-out visitors get nothing. `src/server/rows.ts` maps rows to the admin types. The access checks the rules call (`private.staff_role()`, `private.is_staff()`, `private.staff_can()`, `private.my_artist_id()`, `security definer`) live in the `private` schema, which the API doesn't expose, and only signed-in users may run them; new helper functions get `set search_path = ''` and name everything in full (Supabase's Security Advisor checks both). `npm run check:db` (`scripts/db-check.mts`) runs the migrations on PGlite (Postgres in Node, with Supabase's auth stand-ins) and checks each kind of user's access; add a case there when changing the rules.
- **Server actions** (`src/server/actions/`): `auth.ts` (request and verify an emailed code; staff only if their email is in `staff`), `public.ts` (booking request, artist application: validated, a hidden spam-trap field `website` (not displayed, so autofill can't reach it; a filled one no longer drops the request, because browser autofill once filled it and lost a real order: the record is saved with an internal "check this one" note (`spamNote` in `notify.ts`), the team email subject starts with "[Check: possible spam]" and no confirmation goes to the address typed in; the Resolution Centre form works the same), saved with the secret key), `resolution.ts` (raise, track and escalate a Resolution Centre case; tracking needs the case number plus the email it was raised with and never returns internal notes or staff names), `customer.ts` (My bookings, reviews), `artist.ts` (the artist portal: load, profile, availability, replies to requests, portfolio uploads through one-time signed upload links), `admin.ts` (`adminSession`, `loadAdminDb`, `saveAdminChanges`). In live mode `admin-store.ts` loads the whole `Db` once and each `update()` sends only the records it added, changed or removed, and for changed records only the columns that differ (it sends each record before and after), so two people, or the team and an artist, editing different fields of one record don't undo each other; the server checks the role and row-level security checks it again; a refused save reloads the data and shows why. New records insert (never upsert), so two people taking the same number get an error instead of overwriting each other.
- **One order per request, several artists, artists in several categories** (`…_team_bookings.sql`, `…_one_order_per_request.sql`, `src/lib/booking-needs.ts`, no imports): a request is one booking (one order, B-1215) however many kinds of artist it needs. `items` (a jsonb column) holds one line per category (`BookingItem`: category, service, `count` of artists from 1 to 20 (`MAX_ARTISTS`), and the `artistIds` assigned to that line), so "Photographers × 2, Models × 1, Anchors & Hosts × 1" is one booking with three lines, one quote, one advance and one set of payments. The older columns stay filled from the lines (`src/server/rows.ts` and the booking form): `category` and `service` (the first line), `artists_needed` (all lines added up, at least 1), `artist_ids` (every assigned artist; the live-update trigger `booking_topics()` and the artist portal use it) and `artist_id` (the first). A booking saved before lines existed reads as one line made from those columns (and the seventh migration writes that line). Helpers: `assignedArtists()`, `totalNeeded()`, `itemsLabel()` ("Wedding photography × 2, Bridal makeup") and `itemFor()` (the line an artist is on, or else the first in their categories). An artist or applicant has a main `category` and `otherCategories` (column `other_categories`) they also work in; matching in the admin offers an artist for a booking in any of them (`worksIn()`), and their services can come from any. `withCount()` writes "Photographers × 3" (a single artist shows the name alone) and `needsText()` writes a request's list with every number ("Photographers × 3, Musicians & DJs × 1"), as the WhatsApp message, emails and sheet do. The "How many?" control is `CountPicker` (`src/components/ui/`): 1 to 4 as buttons, then "More" opens a box for up to 20 (more than 20 shows a note to say so in the details).
- **After a save** (`after()` in the actions, `src/server/notify.ts`): a row on the Google Sheet's "All orders" tab for the order (its Category cell lists every line, "Photographers × 2, Models × 1") and a row on the tab named after each of its categories with that line (service account, `ORDERS_SHEET_ID`; the last column is "Artists needed", and a tab whose heading row lacks a newer heading gets it added), and emails through Resend (team notifications follow admin Settings → notify; customers and artists get a confirmation). A job that fails or lacks keys waits in `outbox`; `GET /api/jobs/retry` with `Authorization: Bearer <CRON_SECRET>` retries it (up to 6 times).
- **Live updates** (`src/lib/live.ts`): a trigger on every table (`live_changed()` in the second migration) sends a small "changed" message (table and id, never the record) through Supabase Realtime on private channels: `staff` (every change), `customer:<sha256 of email>` (their bookings and payments), `artist:<id>` (bookings they're shortlisted for or assigned to, their record and replies) and `applicant:<sha256 of email>` (their application). A policy on `realtime.messages` lets each signed-in person join only their own channels (tested in `check:db`). Pages reload their own data through their server actions when a message arrives: the admin (`admin-store.ts`, waiting for its own saves to finish first; a green Live dot in the header), My bookings and the artist portal (`src/lib/artist-live.ts`). Each also reloads when the tab comes back into view and every minute while disconnected. Server-side channel names come from `src/server/live.ts`. Case tracking has no channel (the person isn't signed in), so an open case re-checks every minute.
- **Not live yet**: artist sign-in by WhatsApp code (email codes only), file uploads in the application form (applicants add photos in the portal after signing in), authenticator-app 2FA for staff (email codes for now), DigiLocker KYC and Razorpay.

## Code layout

- **`src/content/site.ts` holds all site copy and data** (categories, services, sample artists, stats, page text), carried over from the old aod.co.in. Pages and components read from it, so copy changes happen there, not in JSX. Ratings, counts and the escrow claim in it are sample data, flagged at the top of the file.
- `src/app/`: routes. The root `layout.tsx` only sets up `<html>`, the two brand fonts, metadata and `MotionProvider`. The customer site lives in the `(site)` route group (the group doesn't change URLs), whose `layout.tsx` adds `Navbar`, `Footer`, `WhatsAppFab` and `ScrollProgress`. In it, `page.tsx` is the homepage, which only composes sections, and `categories/[slug]` is statically built from `categories` through `generateStaticParams`. There are also `book/`, `business/`, `for-artists/` and `about/` (About us: intro with facts drawn from `site.ts`, story, values, the brand strip, the founders with photo placeholders, and a contact grid; copy in `about` in `site.ts`, where the founders' names and titles are flagged to confirm). `not-found.tsx`, `sitemap.ts` and `robots.ts` stay at the root; `not-found.tsx` renders the navbar and footer itself because only the root layout wraps it. The artist portal is `artists/` (see below).
- `src/components/home/`: one file per homepage section. The order follows the visitor's decision path, modelled on booking marketplaces (Urban Company, Upwork): hero (full screen) → announcement bar → stats ("Relied on across Gujarat": four number cards in one font, each with a small graphic picked by `visual` in `stats` (avatars with a check, `Stars` from `ui/Rating.tsx`, category icons, a handshake), with the shared card animation, ending in the "Trusted by renowned brands" logo strip) → category grid → most booked (list) → verified-artists trust section → portals (`Portals`, "Everything in one place": a dark artist band, "Are you an artist? Join AOD.", with perks and two large links, Join as an artist (`/artists/apply`) and Sign in to the artist portal (`/artists`), then three cards with the shared card animation for My bookings, the Resolution Centre and AOD for Business, each showing its address; copy in `portals` in `site.ts`) → the Resolution Centre (`ResolutionFlow`, `#resolution-centre`, in place of the old "How it works": its tagline and intro, Raise a case / Track a case buttons into resolve.aod.co.in, its four steps with `StepFlow`, and its three time promises; copy in `src/content/resolution.ts`; booking's own steps still show beside the booking questions in get-matched) → features (cancellation, reschedule…) → get-matched (intro, a "What happens next" timeline and "Prefer to talk?" on the left, sticky and shown on laptops only; the quiz on the right; copy in `getMatched` in `site.ts`) → booking options (personal / business) → final call to action. `src/app/(site)/page.tsx` comments the reason for each position.
- Brand strip (`src/components/home/BrandStrip.tsx`): logos of brands that trust AOD, listed in `clientBrands` in `site.ts`, scroll without end in two rows (the first half of the list right to left, CSS `animate-marquee`, the second half left to right, `animate-marquee-reverse`, both in `globals.css`; never pauses; still wrapped rows under reduced motion). Logo files are in `public/brands/`, cut out of their backgrounds as transparent PNGs, cropped tight and 160–240px tall. The originals the owner sent are in `context/brands/`. Each logo gets the same visual area rather than the same height, so wide and square logos look balanced. Some logos were adjusted to suit a white strip: HoneyVeda's flower sits to the left of the wordmark, KYB Conmat's white lettering is charcoal, and Ganesh Housing's small print is removed. The GATE 2026 expo logo comes from the expo's own artwork (navy lettering, transparent) and sits in the other row from the round GCCI badge. Mandalam (Mandalam Garba) is its cream card cut out of the maroon Instagram picture. Each row's loop time is worked out from its logos' widths (`SPEED` in `BrandStrip.tsx`), so both rows move at the same speed and adding a logo needs no timing change.
- `src/components/layout/`: navbar (client component, for the mobile menu and the category dropdown; no WhatsApp link, contact is the floating button; "Resolution Centre" (to the homepage section) and "About us" drop out of the desktop bar between 1024 and 1280px), announcement bar, footer (contact: phone, email and the Instagram handle; Follow us: Instagram, LinkedIn, WhatsApp; the LinkedIn icon hides if `brand.linkedinUrl` is empty) and `WhatsAppFab` (bottom-right rounded square with the WhatsApp logo in WhatsApp's own green, `bg-whatsapp` = #25d366, that widens to "Chat on WhatsApp" on hover or keyboard focus).
- `src/components/ui/`: shared building blocks. `Container` sets the page width: small side gutters, capped at `max-w-page` (about 1600px, `--container-page` in `globals.css`) and centred, so very wide or zoomed-out screens don't stretch the layout; section backgrounds sit outside it and still run full width. The navbar's contents use the same cap; the footer is a full-width dark band whose contents use it. `Button` provides `buttonClasses()` and `ButtonLink`, which opens external, `tel:` and `mailto:` links as plain anchors. `Icon` maps icon names from `site.ts` to lucide icons and also draws the WhatsApp, Instagram and LinkedIn SVGs. `PhotoPlaceholder` stands in for real photos. `StepFlow` shows numbered steps without photos (icon badges joined by a line on laptops, a timeline on phones); three or four steps (four columns for four); it's used by the homepage's Resolution Centre section and the For Artists "How joining works" steps. `Rating` shows star ratings.
- Loading (`src/components/ui/Spinner.tsx`, `LoadingBar.tsx`): `Spinner` is a small turning ring in the text colour for every button or line that waits on the server (sign-in codes, the booking quiz's send ("Saving…"), the application, profile, reviews, quotes, cases, tracking, days off); `PageLoader` is the AOD loader (the "A." monogram in a turning orange ring, with a line saying what's loading) for areas that load their data in the browser (My bookings, the artist portal, the admin, the calendar, the Resolution Centre forms). `LoadingBar`, in the root layout, is a thin orange bar across the top from the first paint until the page has fully loaded and on every move to another page (`src/instrumentation-client.ts` sends `aod:navigate` from `onRouterTransitionStart`; the bar ends when the address changes), plus a "Loading…" pill at the bottom when a move takes more than about half a second; quick moves show nothing. The admin header says "Saving…" with a spinner while a change is being saved (`useAdminSaving()`). There are no route-level `loading.tsx` files on purpose: React puts a large page's content behind its loading screen in the built HTML (shown first, swapped by a script), which flashed the spinner on every first visit and left visitors without JavaScript with only the spinner. Keep it that way; give waiting buttons a `Spinner` and loading areas a `PageLoader`.
- Search: `src/lib/fuzzy.ts` holds the ranking and typo tolerance. It has no imports, so it can be tested on its own. Matching works on whole words, sound-alike spellings (ph→f etc.) and edit distance, and categories outrank single services. Search words for each category live in `keywords` in `site.ts`. `src/lib/search.ts` builds the index from `site.ts`. `src/components/search/SearchBox.tsx` is the navbar input with suggestions, arrow-key navigation and a no-match fallback to `/book`. The navbar shows it inline from 1024px up (the "Resolution Centre" and "About us" links hide between 1024 and 1280px to make room); below 1024px it is an always-visible full-width bar under the logo row. While empty and unfocused, the placeholder types random categories and services (word swaps only under reduced motion).
- Interactive parts are small client components (`Navbar`, `SearchBox`, `CityPicker`, `MatchQuiz`, `Coverflow` (via `CategoryCoverflow`), `HeroMotion`, `HeroVideo`, and the artist portal's forms and pages). Everything else is a Server Component, and every route is prerendered as static.
- Animation uses **Motion** (`motion/react`, v14). Shared pieces are in `src/components/motion/`: `Reveal` / `StaggerList` (scroll-in), `TiltCard` (see Cards below), `ScrollProgress`, and `MotionProvider` (sets `reducedMotion="user"` site-wide). Homepage set pieces: one carousel only, the 3D coverflow slide (`src/components/motion/Coverflow.tsx`) for the categories, each card showing the category photo (`image` in `site.ts`, files in `public/categories/`) with the category icon on a small tile; side cards sit further back in 3D so they never cut into the front card. "Most booked services" (`MostBooked`) is a list (the category's symbol on a small light-orange tile that turns orange on hover, service, category, rating, link; two columns on laptops) with no photos and no cards. The carousel supports mouse / touch drag, unlimited trackpad two-finger swipe, dots, arrow buttons and ← → keys (clicking a side card, even two along, brings it to the front and a second click opens it; it only moves by itself while most of it is on screen), the booking walk-through (`HeroMotion`: `HeroDemo` spotlights one step at a time, popping it forward while the other two grey out, cycling every 1.2 s while on screen; all lit and still under reduced motion). The search placeholder types random categories and services (`useTypedPlaceholder` in `SearchBox`).
- Cards: card grids arrive in a wave (a `StaggerList` of `StaggerItem`s), and cards react to the pointer in one of two ways (`src/components/ui/cards.ts`). Cards that open a page (the category carousel, Most booked services, the Portals places, "You can also book" on category pages, the /book choices, the About contacts): on hover an orange border appears, the card takes a light orange tint, the title turns orange and extra bold and the other text bold (`linkCard`, or `linkCardDark` on dark backgrounds, on the card; `linkTitle` on the title; `linkText` on other lines); they don't tilt. Cards that don't open anything (Relied on across Gujarat, the verified checks, Book with confidence, About values and founders, For Business and For Artists reasons, the services on a category page, the booking options): a `TiltCard`, which only tilts towards the pointer, pops up and zooms in a little (`fill={false}` when text sits under the card), with no colour or border change and no glow or light (a white light used to follow the cursor; removed on purpose). Keep class constants that server components use out of "use client" files: such an export reaches a server component as a reference, not a string (the old `cardHover` / `iconHover` once put a function's source into the cards' class names). App lists (My bookings, artist portal, admin) and large panels don't tilt.
- Animated elements render their final content on the server and carry `data-reveal`; a `<noscript>` rule in `layout.tsx` makes them visible when JavaScript is off. Keep both when adding animations.
- Trust message: every artist is described as **thoroughly verified** (`verifiedArtists` in `site.ts`, shown by `VerifiedArtists` in three sizes and the homepage `VerifiedSection`, a plain section like "Book with confidence": label, title, the promise, and the three checks as cards with the shared card animation). The site doesn't promise meeting artists in person, either as a vetting claim or as a customer feature: the "Book with confidence" card and the personal booking option say "Every artist verified thoroughly" instead. (The admin's applicant "Meeting scheduled" stage is the team's internal vetting step.) The hero is the brand name as the page `<h1>`, the subtitle, the verified pill, the two buttons and "Join AOD", full screen and edge to edge over the background video (a light veil keeps the footage about 90% visible, a little darker on the left behind the text; the text is plain white with no shadow or glow, as everywhere on the site; no 3D, no scramble or other text animation), with the booking walk-through on the right in a narrower panel of dark, lightly blurred glass, set a little below centre. The hero is `100svh` minus the sticky navbar, and the announcement bar sits just below it. The footage (GATE 2026 coverage, 20 s: an aerial shot of the expo, then the inaugural session; bright from the first frame, so the loop never dips; `HeroVideo` zooms it 12% from the left edge on every screen but upright phones, which crops off the "Million Minds Tech City" logo in the footage's top-right corner; the phones' cut is the middle of the frame and leaves that corner out already) is in `public/media/`, or at `NEXT_PUBLIC_MEDIA_URL` when that points to a storage bucket or CDN with the same file names: AV1 and H.264 cuts at 1920×1080 (`hero-1080*`, about 2.2 MB AV1 and 3.7 MB H.264, all made from the original 7 MB edit) and 608×1080 for phones held upright (`hero-portrait*`, the middle of the frame, picked by `(max-aspect-ratio: 2/3)`), 30 fps, no sound, plus posters of the first frame as AVIF with WebP for older browsers (`hero.avif` / `hero.webp`, `hero-portrait.avif` / `hero-portrait.webp`). `HeroVideo` renders the poster on the server and only adds the video once the page has loaded, fading it in when it plays; there's no video under reduced motion, Data Saver or 2G. Keep the AV1 files around 2–3 MB (laptop) and 1 MB (phone) when replacing the footage, give the new files new names (`next.config.ts` lets browsers cache `/media` for 30 days), and update the `codecs` levels in `HeroVideo`'s `<source>` tags to match the new files. Matches are "curated matches" (no fixed number).
- Booking flow: every "book" button goes to `/book`, the choosing screen (For personal events / For business). Each choice leads to `/book/personal` or `/book/business`, which run `MatchQuiz` with that audience's occasion list (`occasions` in `site.ts`). `MatchQuiz` asks the three questions one at a time, sliding between them: picking the occasion moves straight on, the answers so far show as chips that jump back to edit, and focus moves to each new question once it has slid in. "Who do you need?" takes any number of categories and, in a "How many of each?" box below, a `CountPicker` and a remove button for each (phones: the name and remove button on one line, the numbers below). Each category page has the same questions in a "Book <category>" section (`#book`, copy in `categoryBooking` in `site.ts`) with its category already picked (`initialNeeds`), so a visitor sets how many and adds other artists for the same event; the page's "Get curated matches" and each service's "Request a quote" scroll to it (they used to open WhatsApp directly, which skipped saving the request).
- **My bookings** (`/my-bookings`, `src/components/bookings/MyBookings.tsx`): the customer's view of their orders, reached from the outlined "My bookings" button in the navbar (icon-only between 1024 and 1280px and on phones) and the phone menu. Sign-in is an emailed 6-digit code. Live: it lists the bookings made with that email (`myOrders`, through the server), shown by request reference and booking id, updates by itself when the team changes something, and saves reviews (`submitReview`); for 2 hours after booking (`customerCancelHours` in `src/content/my-bookings.ts`, checked again by `cancelMyBooking` in `customer.ts`) a "Changed your mind?" box lets the customer cancel the whole order themselves (it notes it on the booking, emails the customer and, unless "Customer cancelled a booking" is off in admin Settings, the team; in the preview it marks the browser's own request cancelled); after that they ask AOD and the refund policy applies (its "How to cancel" says so); each booking links to the Resolution Centre form with its number filled in. Preview: any code works, and it lists the requests this browser sent from the booking form (`src/lib/customer-store.ts`) plus sample bookings labelled "Sample" (`src/content/my-bookings.ts`). Each booking has progress steps, the next action (pay the advance or balance, which asks AOD for the payment details on WhatsApp; download files), event, artist, payments, help and timeline. Browser-kept stores share `createStore` from `src/lib/local-store.ts`.
- City: the navbar `CityPicker` (and `CityChips` in the mobile menu) saves the visitor's city through `src/lib/city.ts`, which keeps it in localStorage (`aod-city`) and reads it with `useSyncExternalStore`. `MatchQuiz` reads the same value, shows "City selected: …" with a Change option instead of asking again, and puts it in the WhatsApp message. In live mode the city is saved with the booking request.
- Artists join by a pre-filled WhatsApp message (`artistJoinMessage` in `site.ts`), or through the artist portal's application form: live, it saves the application and points them to sign in to follow it; preview, it ends with the same WhatsApp hand-off.
- **Artist portal** (`src/app/artists/`, at `artists.aod.co.in`): live on the database when the backend is set up, otherwise a preview. ## Design system

Three colours only: AOD orange (#ff6201), white and black (the whole site, the artist portal, admin and Resolution Centre included, uses them through the tokens in `globals.css`), with the layout modelled on Upwork. Every other shade is a mix of those three (orange with white for tints such as `peach` and `wash`, orange with black for `brand-hover` and `sheen-deep`, black with white for the greys `muted` and `line`); `brand`, `brand-bright`, `apricot` and `tangerine` are all the orange itself, and tints in components use `color-mix()` with a token, never raw colours. Status colours (red errors, green success, amber warnings) and the WhatsApp green stay as they are, because they carry meaning. No text has a shadow or glow behind it, anywhere (the raised `text-shadow-3d` headings, the hero's text shadows, the hero's pointer glow and the For Artists hero's orange glow were all removed on purpose): keep text flat. Smaller headings and card titles (h2/h3 below `text-3xl`, and title spans such as the Portals cards, Most booked services and the `StepFlow` steps) are bold (`font-bold`; uppercase labels `font-semibold`). The announcement bar uses the `bg-sheen` utility (light orange to orange, ink text); the closing call-to-action bands (`FinalCta`, and the For Artists page's own) are flat `bg-brand` with white text, no gradient; both add `grain` for a fine film-grain texture. The AOD wordmark (`public/aod-wordmark.png`) is in the brand orange (`brand`, #ff6201). App icons (in `src/app/`, picked up by Next automatically): the browser-tab icon (`favicon.ico` at 16/32/48 and `icon.png` at 512) is an "A." monogram cut from the wordmark, white on an orange rounded square, because the full "AOD." blurs at 16px; the phone home-screen icon (`apple-icon.png`, 180) shows the full "AOD.". WhatsApp keeps its own green. Use the token classes (`text-ink`, `bg-brand`, `hover:bg-brand-hover`, `bg-peach`, `text-apricot`, `text-tangerine`, `bg-wash`, `border-line`, `text-muted` …), never raw hex values. The brand fonts, loaded with `next/font` in the root `layout.tsx`: **Bricolage Grotesque** for headings (`h1`–`h3` get it in `globals.css`, with its optical-size axis so big headings use the display cut; `font-display` puts it on anything else, such as the stat numbers) and **Montserrat** for all other text (`font-sans`). Real artist photos are the main trust signal, so design cards and pages around photos, not icons. The category photos in `public/categories/` (`image` in `site.ts`) are mock photos for the preview (copied from another working copy of the project; Content & Instagram Reels is an iStock photo, `content-creators.webp`, which needs a licence to stay); replace them with real AOD artists' work before launch. They show in the category carousel and on each category page, where the photo sits on the right of the dark header, fully visible at the right edge and fading into the dark towards the left (a CSS mask). From tablets up the photo box keeps the photo's own shape (`image.width` / `image.height` in `site.ts`) at the header's full height, so nothing is cropped; on phones it fills the header faintly behind the text.

## Rules carried over from the old-site audit

- Never show "received" or "confirmed" for a booking or artist application unless it has actually been saved (to Supabase). Opening WhatsApp is not saving.
- No hardcoded ratings, review counts, artist counts or "bookings" numbers. Show only real data, or leave the element out.
- Don't claim escrow, payments or verification that aren't built yet.
- Don't collect Aadhaar numbers. Identity checks must go through a proper KYC provider such as DigiLocker.
- The site needs privacy, terms and cancellation/refund pages before it collects personal data or payments. Drafts exist (see Policies above); they must be confirmed and reviewed before launch.
- Every page needs a title, a description, Open Graph tags and a share image, because links are mostly shared on WhatsApp. Also provide `sitemap.ts` and `robots.ts`.
- Render key numbers and content on the server so they show up without JavaScript (the old site showed "0 verified artists" to crawlers).
