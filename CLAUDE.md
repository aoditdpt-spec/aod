## Project

A full redesign, from scratch, of **aod.co.in** for AOD (Artists on Demand), an Ahmedabad marketplace for booking photographers, cinematographers, DJs, anchors, makeup artists and other event talent. The goal of the rebuild is a site that feels **more trustworthy** and has real booking and artist data, unlike the old site, which had no backend and only opened WhatsApp.

- `context/brief.md` holds the owner's raw notes for the redesign: features, nav, homepage sections and references. Read it before planning any page.
- `context/*.html` is a saved copy of the Upwork homepage, the main visual reference (layout, colours, typography). Other references: Urban Company, Snabbit, collectui.com.

## Commands

```bash
npm run dev     # dev server at http://localhost:3000
npm run build   # production build (also type-checks)
npm run lint    # ESLint (next/core-web-vitals + typescript)
npm run check:search   # checks search results for common queries and misspellings
npm run check:links    # checks the artist portal's portfolio-link rules and the profile photo's Drive link rules
npm run check:db       # runs the database migrations on PGlite and checks who can read and change what
npm run check:orders   # checks that the booking form's WhatsApp message reads back into the admin's New booking form, and the order IDs
npm run check:markdown # checks the blog and newsletter Markdown reader (what it shows, and that nothing unsafe gets through)
npm run check:xlsx     # checks the password-protected Excel export: an independent decryptor opens it with the password and refuses a wrong one
```

There is no test runner yet. The `scripts/*-check.mts` files are plain Node scripts (run through Node's built-in TypeScript support). Add a case there when you change search keywords or tuning, the link rules, the database's access rules, the booking form's WhatsApp message, the order IDs, the Markdown reader or the Excel encryption.

`docs/DEVELOPER_GUIDE.md` is the guide for human developers (stack, folder by folder, flows, cookbook, errors); keep it in step with changes, like this file.

Copy `.env.example` to `.env.local` and fill it in. Without the Supabase URL and publishable key the site runs as the preview (see Backend below). The setup and testing guides live outside the repo, in `E:\Projects\Internship\aod docs\` (the folder next to this one), because they hold the project's passwords; never move them back into the repo. `backend-setup.md` there is the step-by-step guide to switching the backend on (Supabase project, SQL, first owner, sign-in code emails, keys, Resend, the Google Sheet, retries, subdomains), and `testing.md` is how to test everything: the automated checks, the preview, and a live walk-through across three browsers (staff, customer, artist). Keep it in step when adding a flow.

## Stack

- **Next.js 16 (App Router, `src/` dir) + React 19 + TypeScript.** This version has breaking changes from older Next.js. Check `node_modules/next/dist/docs/` before using an API you're unsure of (e.g. `middleware` is now `proxy`).
- **Tailwind CSS v4.** There is no `tailwind.config`. Design tokens live in the `@theme` block in `src/app/globals.css`.
- **Supabase** for the database and sign-in (emailed 6-digit codes for customers, artists and staff). Use `src/lib/supabase/server.ts` in Server Components/Actions (it acts as the signed-in user, so row-level security applies), `src/lib/supabase/client.ts` in Client Components, and `src/lib/supabase/admin.ts` (secret key, skips row-level security) only in server code after checking the input or the caller. Create a new server client per request.
- **WhatsApp** stays the main contact channel. Build all `wa.me` links through `whatsappUrl()` in `src/lib/whatsapp.ts`.
- HTTPS only: every response carries `Strict-Transport-Security` with `includeSubDomains; preload` (`src/lib/hsts.ts`, sent by `next.config.ts`), and `src/proxy.ts` redirects aod.co.in to www.aod.co.in with that header (aod.co.in must be connected to Production in Vercel's domain settings, not set to redirect, for hstspreload.org to see it). Every subdomain must stay on HTTPS.
- Hosted on Vercel. Visitors are in India, so prefer static or cached rendering, and run server functions in the Mumbai region (`bom1`).

## Backend

- **Two modes**, picked by `backendEnabled` (`src/lib/backend.ts`: the Supabase URL and publishable key are set). Live: every form saves to the database first, sign-in sends real codes, and the admin works on shared data. Preview (no keys): the site behaves as the frontend-only version (WhatsApp hand-off, samples, admin data in the browser). Every live feature keeps its preview fallback, so the deployed site never breaks while keys are missing.
- **Database**: the files in `supabase/migrations/`, each run once in date order in the SQL Editor (`…_init.sql`, `…_live_and_artists.sql`, `…_no_pay_page.sql`, then `…_details_and_developers.sql`, `…_outbox_rule.sql`, `…_team_bookings.sql`, `…_one_order_per_request.sql`, `…_blog_and_newsletter.sql`, `…_artist_brief.sql`, `…_order_ids.sql`, `…_disputes_outside_aod.sql` and `…_artist_photo.sql`; add a new dated file for any change, never edit one that may have been run, and run a new one before deploying the code that uses it). Tables mirror the admin records in `src/lib/admin-store.ts` (applications, artists, bookings, payments, payouts, leads, cases, staff, activity, settings) plus `artist_replies` (an artist's quote or decline for a booking they're shortlisted for), `posts`, `subscribers` and `newsletters` (the blog and newsletter, see below; published posts are the only rows signed-out visitors may read), `outbox` for retries, the public `blog` storage bucket (the blog's photos), and the public `portfolio` storage bucket (artists' photos and videos, listed in `artists.portfolio` / `applications.portfolio`). IDs are the readable references (APP-201, PAY-3101, L-401, RC-1001, U-1; bookings use order IDs such as AOD-PH-102601, see below; a website request is one booking however many kinds of artist it needs, and its ID is also the customer's reference). Row-level security: active staff (listed in `staff`, matched by the signed-in email) read everything; writes need one of the two staff roles, owner (shown as "Admin") or developer (`staff_can()` lets a developer through every owner rule; the policies still list the old ops / finance roles, which the role check no longer allows); customers and artists read nothing directly: My bookings, the artist portal and case tracking go through server actions that check who is signed in and return only what that person should see (no internal notes, shortlists or other people's details); signed-out visitors get nothing. `src/server/rows.ts` maps rows to the admin types. The access checks the rules call (`private.staff_role()`, `private.is_staff()`, `private.staff_can()`, `private.my_artist_id()`, `security definer`) live in the `private` schema, which the API doesn't expose, and only signed-in users may run them; new helper functions get `set search_path = ''` and name everything in full (Supabase's Security Advisor checks both). `npm run check:db` (`scripts/db-check.mts`) runs the migrations on PGlite (Postgres in Node, with Supabase's auth stand-ins) and checks each kind of user's access; add a case there when changing the rules.
- **Server actions** (`src/server/actions/`): `auth.ts` (request and verify an emailed code; staff only if their email is in `staff`), `public.ts` (booking request, artist application: validated, a hidden spam-trap field `website` (not displayed, so autofill can't reach it; a filled one no longer drops the request, because browser autofill once filled it and lost a real order: the record is saved with an internal "check this one" note (`spamNote` in `notify.ts`), the team email subject starts with "[Check: possible spam]" and no confirmation goes to the address typed in; the Dispute Desk form works the same), saved with the secret key), `resolution.ts` (raise, track and escalate a Dispute Desk case; tracking needs the case number plus the email it was raised with and never returns internal notes or staff names), `customer.ts` (My bookings, reviews), `artist.ts` (the artist portal: load, profile, availability, replies to requests, portfolio uploads through one-time signed upload links), `admin.ts` (`adminSession`, `loadAdminDb`, `saveAdminChanges`; changing a post refreshes the blog's cached pages with `revalidatePath`), `newsletter.ts` (sign-up, confirm, unsubscribe, and sending an issue) and `blog.ts` (one-time upload links for the blog's photos, staff only). `src/server/staff.ts` (`currentStaff()`) is the staff check they share. In live mode `admin-store.ts` loads the whole `Db` once and each `update()` sends only the records it added, changed or removed, and for changed records only the columns that differ (it sends each record before and after), so two people, or the team and an artist, editing different fields of one record don't undo each other; the server checks the role and row-level security checks it again; a refused save reloads the data and shows why. New records insert (never upsert), so two people taking the same number get an error instead of overwriting each other.
- **One order per request, several artists, artists in several categories** (`…_team_bookings.sql`, `…_one_order_per_request.sql`, `src/lib/booking-needs.ts`, no imports): a request is one booking (one order) however many kinds of artist it needs. **Order IDs** (`src/lib/order-id.ts`, no imports, tested by `check:orders`): AOD-<two-letter category code>-<MMYY><number>, such as AOD-PH-102601 (month and year the order was made, India time; the number counts every order of the year whatever its category, 01–99 then 100…, and restarts at 01 each January); an order of several categories is AOD-MIX-…, and each line's ID is the same number with its own code (`lineId()`: AOD-DR-102602 of AOD-MIX-102602), used on the category sheet tabs, the drawer's line blocks, artists' WhatsApp messages and the artist portal. The ID is also the customer's reference (`request_ref`). The website saves through `insertOrder()` (`src/server/ids.ts`), the admin through `newOrderId()`; the tenth migration's unique index refuses a second order with the same year and number. Orders made before keep B-1215 / AOD-1215; add a code to `categoryCodes` for a new category. `items` (a jsonb column) holds one line per category (`BookingItem`: category, service, `count` of artists from 1 to 20 (`MAX_ARTISTS`), and the `artistIds` assigned to that line), so "Photographers × 2, Models × 1, Anchors & Hosts × 1" is one booking with three lines, one quote, one advance and one set of payments. The older columns stay filled from the lines (`src/server/rows.ts` and the booking form): `category` and `service` (the first line), `artists_needed` (all lines added up, at least 1), `artist_ids` (every assigned artist; the live-update trigger `booking_topics()` and the artist portal use it) and `artist_id` (the first). A booking saved before lines existed reads as one line made from those columns (and the seventh migration writes that line). Helpers: `assignedArtists()`, `totalNeeded()`, `itemsLabel()` ("Wedding photography × 2, Bridal makeup") and `itemFor()` (the line an artist is on, or else the first in their categories). An artist or applicant has a main `category` and `otherCategories` (column `other_categories`) they also work in; matching in the admin offers an artist for a booking in any of them (`worksIn()`), and their services can come from any. `withCount()` writes "Photographers × 3" (a single artist shows the name alone) and `needsText()` writes a request's list with every number ("Photographers × 3, Musicians & DJs × 1"), as the WhatsApp message, emails and sheet do. The "How many?" control is `CountPicker` (`src/components/ui/`): 1 to 4 as buttons, then "More" opens a box for up to 20 (more than 20 shows a note to say so in the details).
- **After a save** (`after()` in the actions, `src/server/notify.ts`): a row on the Google Sheet's "All orders" tab for the order (its Category cell lists every line, "Photographers × 2, Models × 1") and a row on the tab named after each of its categories with that line (service account, `ORDERS_SHEET_ID`; the last column is "Artists needed", and a tab whose heading row lacks a newer heading gets it added), and emails through Resend (team notifications follow admin Settings → notify and go to `TEAM_EMAIL` plus every active Admin in Team & roles, `teamEmails()` in `notify.ts`; customers and artists get a confirmation). A job that fails or lacks keys waits in `outbox`; `GET /api/jobs/retry` with `Authorization: Bearer <CRON_SECRET>` retries it (up to 6 times).
- **Live updates** (`src/lib/live.ts`): a trigger on every table (`live_changed()` in the second migration) sends a small "changed" message (table and id, never the record) through Supabase Realtime on private channels: `staff` (every change), `customer:<sha256 of email>` (their bookings and payments), `artist:<id>` (bookings they're shortlisted for or assigned to, their record and replies) and `applicant:<sha256 of email>` (their application). A policy on `realtime.messages` lets each signed-in person join only their own channels (tested in `check:db`). Pages reload their own data through their server actions when a message arrives: the admin (`admin-store.ts`, waiting for its own saves to finish first; a green Live dot in the header), My bookings and the artist portal (`src/lib/artist-live.ts`). Each also reloads when the tab comes back into view and every minute while disconnected. Server-side channel names come from `src/server/live.ts`. Case tracking has no channel (the person isn't signed in), so an open case re-checks every minute.
- **Not live yet**: artist sign-in by WhatsApp code (email codes only), file uploads in the application form (applicants add photos in the portal after signing in), authenticator-app 2FA for staff (email codes for now), DigiLocker KYC and Razorpay.

## Code layout

Pages and components read from it, so copy changes happen there, not in JSX. Ratings, counts and the escrow claim in it are sample data, flagged at the top of the file.

The customer site lives in the `(site)` route group (the group doesn't change URLs), whose `layout.tsx` adds `Navbar`, `Footer`, `WhatsAppFab` and `ScrollProgress`. In it, `page.tsx` is the homepage, which only composes sections, and `categories/[slug]` is statically built from `categories` through `generateStaticParams`. The artist portal is `artists/` (see below).
- `src/components/home/`: one file per homepage section. - Brand strip (`src/components/home/BrandStrip.tsx`): logos of brands that trust AOD, listed in `clientBrands` in `site.ts`, scroll without end in two rows (the first half of the list right to left, CSS `animate-marquee`, the second half left to right, `animate-marquee-reverse`, both in `globals.css`; never pauses; still wrapped rows under reduced motion). Logo files are in `public/brands/`, cut out of their backgrounds as transparent PNGs, cropped tight and 160–240px tall. The originals the owner sent are in `context/brands/`. Each logo gets the same visual area rather than the same height, so wide and square logos look balanced. Some logos were adjusted to suit a white strip: HoneyVeda's flower sits to the left of the wordmark, KYB Conmat's white lettering is charcoal, and Ganesh Housing's small print is removed. - `src/components/layout/`: navbar (client component, for the category dropdown, the city and the back button; below 1024px it is an app-style top bar: a back arrow on every page but the homepage (back within the site, or home when the visitor came from elsewhere), the logo, the city as a pill (`CitySheetButton`, which opens the cities in a bottom sheet) and the search bar under them; there is no hamburger menu any more (it stayed open over the page after a tap), the bottom tab bar's More sheet does that job; no WhatsApp link, contact is the floating button; every link shows from 1024px: below 1280px the links are a little smaller and the city picker only appears from 1152px (the booking questions ask for the city when it isn't picked); "Dispute Desk" opens resolve.aod.co.in (`portalHref("/resolve")`); the footer's "Have a dispute?" - `src/components/ui/`: shared building blocks. `Container` sets the page width: small side gutters, capped at `max-w-page` (about 1600px, `--container-page` in `globals.css`) and centred, so very wide or zoomed-out screens don't stretch the layout; section backgrounds sit outside it and still run full width. The navbar's contents use the same cap; the footer is a full-width dark band whose contents use it. `Button` provides `buttonClasses()` and `ButtonLink`, which opens external, `tel:` and `mailto:` links as plain anchors. `Icon` maps icon names from `site.ts` to lucide icons and also draws the WhatsApp, Instagram and LinkedIn SVGs. `PhotoPlaceholder` stands in for real photos. `StepFlow` shows numbered steps without photos (icon badges joined by a line on laptops, a timeline on phones); three or four steps (four columns for four); it's used by the homepage's Dispute Desk section and the For Artists "How joining works" steps. `Rating` shows star ratings.
- Loading (`src/components/ui/Spinner.tsx`, `LoadingBar.tsx`): `Spinner` is a small turning ring in the text colour for every button or line that waits on the server (sign-in codes, the booking quiz's send ("Saving…"), the application, profile, reviews, quotes, cases, tracking, days off); `PageLoader` is the AOD loader (the "A." monogram in a turning orange ring, with a line saying what's loading) for areas that load their data in the browser (My bookings, the artist portal, the admin, the calendar, the Dispute Desk forms). `LoadingBar`, in the root layout, is a thin orange bar across the top from the first paint until the page has fully loaded and on every move to another page (`src/instrumentation-client.ts` sends `aod:navigate` from `onRouterTransitionStart`; the bar ends when the address changes), plus a "Loading…" pill at the bottom when a move takes more than about half a second; quick moves show nothing. The admin header says "Saving…" with a spinner while a change is being saved (`useAdminSaving()`). There are no route-level `loading.tsx` files on purpose: React puts a large page's content behind its loading screen in the built HTML (shown first, swapped by a script), which flashed the spinner on every first visit and left visitors without JavaScript with only the spinner. Keep it that way; give waiting buttons a `Spinner` and loading areas a `PageLoader`.
- Search: the typing placeholder writes straight into the page (no React re-render per letter) and pauses while its box is off screen or hidden. `src/lib/fuzzy.ts` holds the ranking and typo tolerance. It has no imports, so it can be tested on its own. Matching works on whole words, sound-alike spellings (ph→f etc.) and edit distance, and categories outrank single services. Search words for each category live in `keywords` in `site.ts`. `src/lib/search.ts` builds the index from `site.ts`. `src/components/search/SearchBox.tsx` is the navbar input with suggestions, arrow-key navigation and a no-match fallback to `/book`. The navbar shows it inline from 1024px up (beside every link; the city picker waits until 1152px to make room); below 1024px it is an always-visible full-width bar under the logo row. While empty and unfocused, the placeholder types random categories and services (word swaps only under reduced motion).
- Interactive parts are small client components (`Navbar`, `SearchBox`, `CityPicker`, `MatchQuiz`, `Coverflow` (via `CategoryCoverflow`), `HeroVideo`, `AppTabBar`, `Sheet`, `ScrollRow`, and the artist portal's forms and pages). Everything else is a Server Component, and every route is prerendered as static.

"Most booked services" (`MostBooked`) is, on tablets, a sideways row of cards modelled on Headout's experience cards (`ScrollRow` in `src/components/ui/`: heading on the left, See all and round ← → buttons on the right, cards snapping into place; phones get a list with the photo on the left; laptops get the phone's list in two columns: a white card per service with its photo on the left, the service, category, rating and "Get a quote", `MostBookedList`): the category photo with a "Verified artists" badge, "★ rating (bookings) · category", the service, two promises with icons, and "Get a quote" where Headout shows a price; each opens the category page's booking questions; each shows the service's own photo when `mostBooked` in `site.ts` gives one (`image`, files in `public/services/`: Event photography, Party makeup and Candid photography, AI-generated mock photos with Gemini's corner watermark cropped off, to replace with real work before launch), or else its category's; copy in `mostBookedSection` in `site.ts`. The carousel supports mouse / touch drag, unlimited trackpad two-finger swipe, dots, arrow buttons and ← → keys (clicking a side card, even two along, brings it to the front and a second click opens it; it only moves by itself while most of it is on screen). The search placeholder types random categories and services (`useTypedPlaceholder` in `SearchBox`).
- Cards: card grids arrive in a wave (a `StaggerList` of `StaggerItem`s), and cards react to the pointer in one of two ways (`src/components/ui/cards.ts`). Cards that open a page (the category carousel, Most booked services, the Portals places, "You can also book" on category pages, the /book choices, the About contacts): on hover an orange border appears, the card takes a light orange tint, the title turns orange and extra bold and the other text bold (`linkCard`, or `linkCardDark` on dark backgrounds, on the card; `linkTitle` on the title; `linkText` on other lines); they don't tilt. Cards that don't open anything (Relied on across Gujarat, the verified checks, Book with confidence, About values and founders, For Business and For Artists reasons, the services on a category page, the booking options): a `TiltCard`, which only tilts towards the pointer, pops up and zooms in a little (`fill={false}` when text sits under the card), with no colour or border change and no glow or light (a white light used to follow the cursor; removed on purpose). Keep class constants that server components use out of "use client" files: such an export reaches a server component as a reference, not a string (the old `cardHover` / `iconHover` once put a function's source into the cards' class names). App lists (My bookings, artist portal, admin) and large panels don't tilt.

- Booking requests and artist applications save to the database first (live mode) and only then say "received" with their reference; WhatsApp still opens afterwards (through `whatsappUrl()`, with the reference in the message), and if saving fails the visitor is told and WhatsApp carries the request instead. So that every order that reaches WhatsApp also reaches the admin: the quiz's send control is a `<button>` (a wa.me link could be opened in a new tab and skip the save); a dropped connection gets one retry; when saving fails the WhatsApp message ends "Ref: not saved on the website" and the server emails the team the whole request (straight through Resend, not the database); the message carries the phone number too. The admin's New booking form has a "Paste a WhatsApp message" box that fills every field from such a message (`src/lib/whatsapp-order.ts`, no imports, tested by `check:orders`; it reads "Photographers × 3" and hand-typed forms such as "3 x Photographers" or "Photographers (3)", and a message without numbers as one of each; a request for several categories becomes one booking with a line for each, with a note that it came from WhatsApp). New booking itself lists "Who they need" as lines of category, service and how many (`CountPicker`), with "Add another category", and creates one booking with those lines. Chats started with the WhatsApp button (not the form) never reach the site; the team adds those with New booking. Before a website request is saved its email is confirmed with an emailed 6-digit code, against bots: the quiz's send button first emails the code (`requestCode(email, "customer")`) and shows a code box, and "Confirm & send" checks it (`verifyCode`, which also signs the visitor in to My bookings; someone already signed in with that email skips it); `createBookingRequest()` refuses a request whose email isn't the signed-in one (`verify: true`); if the code can't be sent, the request can still go to WhatsApp marked "not saved"; preview: no email, any 6 digits. After the event details the quiz has an optional **"Brief for the artists"** box (`src/components/home/ArtistBrief.tsx`, wording in `src/content/artist-brief.ts`, which has no imports): one text box the customer writes in, with no preset questions (removed on request), saved as the brief's `note`. The older per-category quick questions, preferences and reference links stay in `artist-brief.ts` only so earlier bookings' briefs still read correctly. `cleanBrief()` keeps only known questions and choices (in the form and again on the server), and the answers are saved in the booking's `brief` column (jsonb, ninth migration; until it's run the server saves the brief into the notes instead). The brief travels with the order: the WhatsApp message ("Brief for the artists:" lines after the details, so a pasted message keeps it in the admin's notes; tested by `check:orders`), the team and customer emails, the sheet's last column "Brief" (each category's tab gets its part), the admin booking drawer's "Brief for the artists" section, the "new request" WhatsApp message to an artist (their part), and the artist portal's request card ("The customer's brief": their category's answers and the shared ones). Once a request has gone (saved, or sent on WhatsApp when saving failed), the questions make way for a confirmation (the reference, View in My bookings, Open WhatsApp again, Book another event). My bookings has **Book again** on every order (`src/lib/rebook.ts`, sessionStorage): it opens `/book/<audience>` with that order's occasion, artists and counts, city, times and details filled in and the event-details step open, so only the new date is left. Every field of an event request is required, on the website's booking quiz and the admin's New booking form alike: date (from tomorrow), start and end time, city, event details, name, phone and email (venue and budget are optional in the admin). The website's quiz asks for a start time and "How many hours?" (half hours up to 12, then whole hours up to 24) and works the end time out (`endAfter()` in `event-time.ts`); the admin's New booking still takes start and end. Times are stored as HH:MM start and end (`time` / `endTime`, columns `event_time` / `event_end_time`; an end earlier than the start means the event runs past midnight) and shown through `src/lib/event-time.ts` (no imports) as "8:00 PM – 1:00 AM (5 hours, ends next day)" in the forms, WhatsApp message, emails, the sheet's Time column, the admin and My bookings.

## Design system

Three colours only: AOD orange (#ff6201), white and black (the whole site, the artist portal, admin and Dispute Desk included, uses them through the tokens in `globals.css`), with the layout modelled on Upwork. Every other shade is a mix of those three (orange with white for tints such as `peach` and `wash`, orange with black for `brand-hover` and `sheen-deep`, black with white for the greys `muted` and `line`); `brand`, `brand-bright`, `apricot` and `tangerine` are all the orange itself, and tints in components use `color-mix()` with a token, never raw colours. Status colours (red errors, green success, amber warnings) and the WhatsApp green stay as they are, because they carry meaning. No text has a shadow or glow behind it, anywhere (the raised `text-shadow-3d` headings, the hero's text shadows, the hero's pointer glow and the For Artists hero's orange glow were all removed on purpose): keep text flat. Smaller headings and card titles (h2/h3 below `text-3xl`, and title spans such as the Portals cards, Most booked services and the `StepFlow` steps) are bold (`font-bold`; uppercase labels `font-semibold`). The announcement bar uses the `bg-sheen` utility (light orange to orange, ink text); the closing call-to-action bands (`FinalCta`, and the For Artists page's own) are flat `bg-brand` with white text, no gradient; both add `grain` for a fine film-grain texture. The AOD wordmark (`public/aod-wordmark.png`) is in the brand orange (`brand`, #ff6201); pages show `public/aod-wordmark-sm.png` (84px tall) with `unoptimized`, because Next.js's small AVIF copy of the logo turned the orange brown. App icons (in `src/app/`, picked up by Next automatically): the browser-tab icon (`favicon.ico` at 16/32/48 and `icon.png` at 512) is an "A." monogram cut from the wordmark, white on an orange rounded square, because the full "AOD." blurs at 16px; the phone home-screen icon (`apple-icon.png`, 180) shows the full "AOD.". WhatsApp keeps its own green. Use the token classes (`text-ink`, `bg-brand`, `hover:bg-brand-hover`, `bg-peach`, `text-apricot`, `text-tangerine`, `bg-wash`, `border-line`, `text-muted` …), never raw hex values. The brand fonts, loaded with `next/font` in the root `layout.tsx`: **Bricolage Grotesque** for headings (`h1`–`h3` get it in `globals.css`, with its optical-size axis so big headings use the display cut; `font-display` puts it on anything else, such as the stat numbers) and **Montserrat** for all other text (`font-sans`). Real artist photos are the main trust signal, so design cards and pages around photos, not icons. The category photos in `public/categories/` (`image` in `site.ts`) are mock photos for the preview (copied from another working copy of the project; Content & Instagram Reels is an iStock photo, `content-creators.webp`, which needs a licence to stay); replace them with real AOD artists' work before launch. They show in the category carousel and on each category page, where the photo sits on the right of the dark header, fully visible at the right edge and fading into the dark towards the left (a CSS mask). From tablets up the photo box keeps the photo's own shape (`image.width` / `image.height` in `site.ts`) at the header's full height, so nothing is cropped; on phones it fills the header faintly behind the text.

## Rules carried over from the old-site audit

- Never show "received" or "confirmed" for a booking or artist application unless it has actually been saved (to Supabase). Opening WhatsApp is not saving.
- No hardcoded ratings, review counts, artist counts or "bookings" numbers. Show only real data, or leave the element out.
- Don't claim escrow, payments or verification that aren't built yet.
- Don't collect Aadhaar numbers. Identity checks must go through a proper KYC provider such as DigiLocker.
- The site needs privacy, terms and cancellation/refund pages before it collects personal data or payments. Drafts exist (see Policies above); they must be confirmed and reviewed before launch.
- Every page needs a title, a description, Open Graph tags and a share image, because links are mostly shared on WhatsApp. Also provide `sitemap.ts` and `robots.ts`.
- Render key numbers and content on the server so they show up without JavaScript (the old site showed "0 verified artists" to crawlers).
